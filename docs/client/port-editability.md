# Java port editability assessment

**Applies to:** the `0.1.2` source tree. Last reviewed: 2026-10-25.


Findings are **[hypothesis: port]**, based on the packaged PC port and `src/`, not a clean APK or gameplay observation. Launcher `--help` was run, but the game window was not started.

## 1. Sources and project files

**[hypothesis: port]** The port folder has no Java/Kotlin sources or build project. The separate `src/` tree contains **644 `.java` files** across the game, compatibility layers, and launcher modules; LWJGL is provided only as external JARs, and `runtime/`, `lib/` and `game-assets-ios/` are supplied externally at release time. There are no Maven/Gradle/Ant build descriptors or IDE project files; the build script is `tools/build-client.ps1`.

## 2. Class metadata and naming

**[hypothesis: port]** Samples from `game-ios.jar`, `launcher.jar`, `compat-ios.jar`, and `compat-android.jar` are class major **65** (Java 21); a `platform-1001.jar` sample is major **50** (Java 6). `LevelDefinition` and `ZombieCharacter` have both `LineNumberTable` and `LocalVariableTable`; sampled launcher/compat classes do too, while the platform sample lacks them. `IosPlatform` is an interface, with no method bodies/debug tables.

Names are mostly readable (`ZombieCharacter`, `getXpLimit`, `mXpLimit`, `zlport.ios.IosPlatform`), not broadly obfuscated. Decompiled parameter names like `var1` remain. The `src/game-ios` tree has 380 Java files for 379 JAR classes; the difference is consistent with inner/anonymous class files.

## 3. Provenance and decompilation quality

**[hypothesis: port]** `platform-1001.jar` embeds `META-INF/zlport/game-core.properties`, stating “generated by zlport.apkimport” and recording 437 dropped / 111 kept classes. This supports automated APK-import processing, not a conclusion that all game logic was automatically translated or hand-written; exact provenance is **unclear**. `src/platform-1001` contains Vineflower diagnostic comments, identifying Vineflower as a decompiler used for at least some sources.

The requested samples exist in `src/` and read as Java: `LevelDefinition`, `ZombieCharacter`, and `Tuner` retain descriptive fields and structured control flow; `IosPlatform` has readable method signatures; `ResourceIDs` is a large constants interface. These samples look decompilable/readable, but recompilation was not tested.

There are important gaps: at least **50** methods across five `game-ios` source files explicitly throw `UnsupportedOperationException` (“sem código na 1.4.4”). Spot checks of `Toolkit.getImage` and `ServerSocketMessage.getBytes` confirm those throws are also in the JAR bytecode—not merely decompiler failures. `Graphics3D.java` additionally shows Vineflower warnings for synchronized blocks in the platform layer.

## 4. Architecture and launch

**[hypothesis: port]** JAR manifests have no `Main-Class` or `Class-Path`. `ZombieLane.exe --help` identifies the active launcher as `zombie-lane-ios`, with a fixed 1136x640 logical screen and an adjacent `game-assets-ios` bundle. This matches `launcher-ios.jar`'s `zlport.launcher.IosMain`, which installs `PcIosPlatform` and `IosDriver` before starting `com.dchoc.DCiDead` through the shared GLFW launcher. The help output was also reproduced by directly invoking `zlport.launcher.IosMain` with the bundled Java 21 runtime and `lib/*` classpath. The native EXE's exact JVM arguments were not recovered; see [PC port execution](./pc-execution.md) for the verified direct invocation and startup flow.

`game-ios.jar` contains game logic (379 classes). `launcher-ios.jar` is the active entrypoint; it reuses `launcher.jar` for windowing, input, the game loop, and OpenGL presentation. LWJGL 3.4.3 supplies desktop windowing, graphics, and audio. `runtime-ios.jar` plus `compat-ios.jar` adapt the iOS-facing game APIs to PC; `compat-android.jar`, `j2me-desktop.jar`, `gles-desktop.jar`, and `audio-desktop.jar` provide additional platform/legacy APIs. `platform-1001.jar` is a separate imported platform layer, not the `IosMain` game entrypoint. Coupling is material: `DCiDead` calls `Ios.platform().getNeedUpdate()` directly; game rendering uses `Toolkit`, `IRenderingPlatform`, and `javax.microedition` APIs.

## 5. Toolchain

**[hypothesis: port]** The bundled runtime image is a JetBrains Runtime **21.0.8** JRE; its curated module list suggests a trimmed image, and it does not provide the build compiler. The release build uses a separate JDK 21 or newer (`javac`; verified with Temurin 25). Compiling major-65 classes requires JDK 21 or newer.

## 6. Size and complexity

**[hypothesis: port]** `game-ios.jar` is 1,412,267 bytes. Its largest class files are `ResourceIDs` (1,205,070 bytes), `CsvIDs` (443,626), and `TextIDs` (162,092); corresponding Java sources are about 1.06 MB / 21,018 lines, 368 KB / 12,511 lines, and 137 KB / 3,056 lines. Largest behavior sources include `MenuObject` (1,721 lines), `IsometricScene` (1,395), and `PlayerProfile` (923). Sampled bytecode includes large methods (`GameEngine.getArea`, maximum observed offset 5,560) and switches/branches, but the decompiled game sources inspected have ordinary structured loops rather than obvious goto-style output.

## Verdict

**B) Editable after decompile + recompile — moderate confidence.** Decompiled Java for the game and support modules is already present and generally readable, so edits need not start from the IPA. It is not a complete Java project: no build configuration, recompilation unverified, and several packaged methods are explicit stubs. Compared with decompiling the IPA from scratch, this saves recovering/naming much of the game logic and exposes resource IDs and the desktop adapter. Risks are decompiled/generated-code quality, missing method implementations, tight platform-emulation coupling, Java 21 requirements, and possible APK/IPA patch contamination; the importer’s filtering metadata does not establish patch cleanliness.
