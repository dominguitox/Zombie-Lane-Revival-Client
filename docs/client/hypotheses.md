### Zombie behavior

- **Claim:** Zombies move on a random delay of 1750-2250 time units and use
  Chebyshev tile distance (max of column/row difference).
- **Source:** [hypothesis: port] (ZombieCharacter, bytecode)
- **Status:** open. The decompiled Flash zombie AI uses the same 1.75-2.25 s
  interval [code-read: flash-decompile], which shows design similarity; it does
  not verify the port. The port's time-unit mapping and the Chebyshev-distance
  reading remain unverified.

- **Claim:** Player speed is 225.0 and zombie speed is 37.5.
- **Source:** [hypothesis: port] (Tuner.init)
- **Status:** open. The Flash client uses its own speed scale (world px/s on a
  64-px grid) [code-read: flash-decompile], so its numbers cannot verify the
  port's constants.

### Game state and persistence

- **Claim:** `GameEngine` behaves like a state machine centered on a loading
  phase (`0`), area transition (`1`), play states (`2`/`4`/`6`), intro
  (`7`/`8`), and a save/travel phase (`9`). The state change code reconfigures
  input blocking, music, loading screen, notifications, and first-visit
  tracking.
- **Source:** [hypothesis: port] (`GameEngine.java`)
- **Status:** open - the decompiled flow is internally consistent, but exact UX
  timings were not observed in-game.

- **Claim:** Save flow is tied to `pauseGame()`, `resumeGame()`, and a deferred
  `mSaveGameState` flag. On pause it persists the profile and area state when
  the tutorial is complete; on resume it recreates the session, replays the
  loading state, and reactivates area music.
- **Source:** [hypothesis: port] (`GameEngine.java`)
- **Status:** open - this describes the port's lifecycle semantics, not the
  original mobile UX.

### Data format and tables

- **Claim:** Game balance (levels, combos, areas) is read from binary resources
  via Toolkit.getResourceByteArray, not from code or CSV.
- **Source:** [hypothesis: port] (Tuner, bytecode)
- **Status:** open. Both clients are data-file-driven: the Flash client loads
  tuning, combos, areas, and missions from external data files
  [code-read: flash-decompile], while the port uses packed binary resources.
  That is design similarity, not verification, and the port's binary layout
  remains its own schema.

- **Claim:** Resource file r1 is a packed archive (big-endian): bytes 0-3 = file
  size, bytes 4-7 = entry count (14952), then a table of 4-byte offsets from the
  start of the file. Entry index = resource ID & 0xFFFF.
- **Source:** [hypothesis: port + IPA] (Toolkit loader bytecode, checked
  structurally against r1)
- **Status:** open (structure matches; contents unverified).

- **Claim:** Entry 14897 (ID 80433) is the level table: 102 records (levels
  0-101) of 29 bytes. XP limit goes from 0 (levels 0-1) to 1,600,000 (level 100);
  level 101 holds 9,999,999, probably a sentinel.
- **Source:** [hypothesis: IPA]
- **Status:** open - field meanings unverified.

- **Claim:** Entry 14895 (ID 80431) is the combo table: 11 records (levels 0-10),
  required items 0, 9, 20...100, rewards 0, 5, 10...50, reward type 9.
- **Source:** [hypothesis: IPA]
- **Status:** open. The Flash client also ships an item-combo ladder
  [code-read: flash-decompile]. The match shows design similarity; the port's
  11-record table itself remains unverified.

- **Claim:** Level 0 is identical to level 1 except its number and may be a
  placeholder.
- **Source:** [hypothesis: IPA]
- **Status:** open.

## Cross-source notes

Matching values in two unverified sources show design similarity, not
verification. Each entry keeps its own status.

- The zombie delay (1.75-2.25 s), four-tier achievement chains, crafted-only
  zombies, and the item-combo ladder appear in both the port material and the
  decompiled Flash client. These matches are useful design comparisons, but they
  do not verify the port's constants or byte-level tables.
- Both clients use data files and named mission counters. The port's packed
  binary layout and counter mappings remain open.
- A shared `/dead/<Service>` host shape appears in an archived Facebook capture
  and in the port's war history. Only the host shape matches; transport formats
  remain incompatible. The archive capture keeps its legacy
  `[observed: Wayback]` label.
